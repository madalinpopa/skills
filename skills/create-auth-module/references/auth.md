# Auth module anatomy

The auth module owns user accounts, sessions, and the caller's profile. It is
a normal module of the layout: its own OpenAPI spec, Postgres schema,
migrations, and tests, plus one contract for the rest of the API. The script
writes this tree:

```
api/internal/modules/auth/
├── module.go                  Module implementation; wires the services, embeds the migrations
├── config.go                  Config, Validate, and ConfigFromEnv
├── contract.go                Contract implementing modules.Auth
├── domain/
│   ├── user.go                User, UserUUID, NewUser, NormalizeEmail
│   ├── token.go               RefreshToken, TokenUUID, expiry and revocation rules
│   ├── errors.go              every sentinel error the handlers map
│   └── repository.go          UserRepository and TokenRepository
├── app/
│   ├── command.go             Register, Login, Refresh, Logout
│   ├── query.go               GetUser
│   ├── token.go               access and refresh token ports, HashToken
│   ├── password.go            bcrypt HashPassword and VerifyPassword
│   ├── context.go             Identity on the request context
│   └── command_test.go        rotation, replay, and logout rules with in-memory fakes
├── adapters/
│   ├── jwtx/                  HS256 access tokens: Issue and Verify, with a test
│   ├── refreshtx/             opaque refresh tokens: random bytes plus hash, with a test
│   ├── rest/
│   │   ├── openapi.yaml       the five routes below
│   │   ├── oapi-codegen.yaml  echo5-server, strict-server, models
│   │   ├── handler.go         Handler, NewHandler, Register, cookie settings
│   │   ├── middleware.go      bearer middleware with the public operation list
│   │   ├── auth.go            Login, Refresh, Logout
│   │   ├── user.go            RegisterUser, GetMe
│   │   ├── server/            generated: server.gen.go
│   │   └── client/            client.go, oapi-codegen.yaml, generated client.gen.go
│   └── pgstore/
│       ├── sqlc.yaml          pgx/v5, typed UUID overrides
│       ├── sqlc.go            go:generate go tool sqlc generate
│       ├── migrations/        0001_init_auth.up.sql: auth.users, auth.refresh_tokens
│       ├── queries/           users.sql, refresh_tokens.sql
│       ├── models/            generated by sqlc
│       ├── user_repo.go       UserRepository; maps the unique email to ErrEmailTaken
│       └── token_repo.go      TokenRepository; Rotate runs in one transaction
└── tests/
    ├── setup_test.go          TestMain: container, wire the module, serve
    ├── helpers_test.go        client, bearer editor, register and login helpers
    └── auth_test.go           register, login, cookie, refresh, replay, logout, 401s
```

## Routes

| Route | Auth | Result |
| --- | --- | --- |
| `POST /auth/register` | public | 201 with the user UUID; 400 on bad input; 409 when the email exists |
| `POST /auth/login` | public | 200 with a session; 401 `invalid-credentials` for a wrong password or unknown email |
| `POST /auth/refresh` | public | 200 with a new session; 401 `invalid-refresh-token` |
| `POST /auth/logout` | bearer | 204; 400 when no refresh token was presented |
| `GET /auth/me` | bearer | 200 with the caller's profile; 404 when the user is gone |

A session response carries the access token, `Bearer`, the lifetime in
seconds, and the user UUID. The refresh token travels differently per client:

- Web clients, the default, get it as an HttpOnly cookie named
  `refresh_token` with `Path=/auth`, and send it back automatically. Logout
  clears the cookie.
- Clients that send `X-Client-Type: mobile` get it in the `refresh_token`
  field of the body and send it back in the request body of refresh and
  logout.

Each client type has one transport only, so a stray cookie cannot act for a
mobile client. Session responses are sent with `Cache-Control: no-store`.

## Tokens

Access tokens are HS256 JWTs with issuer, audience, subject, `jti`, `iat`,
`nbf`, and `exp`. Verification requires all of them and checks the method,
issuer, and audience. They are stateless: logout does not invalidate them,
they simply expire. Keep the lifetime short; the default is 15 minutes.

Refresh tokens are 32 random bytes, sent base64url encoded. Only the SHA-256
hash is stored, so a leaked database does not leak sessions. Every refresh
rotates: the presented token is revoked and a replacement is stored in one
transaction. The conditional update `WHERE revoked_at IS NULL` takes the row
lock, so two concurrent refreshes of one token cannot both succeed; the loser
gets `ErrRefreshTokenRotated`.

A refresh token presented after it was revoked is a replay. Somebody else
already holds the replacement, so the module revokes every refresh token of
that user and returns 401. The user logs in again on every device. An expired
but unrevoked token is only refused.

Passwords are bcrypt hashes at cost 12, between 8 characters and 72 bytes.
Login verifies a dummy hash when the email is unknown, so timing does not
reveal which addresses are registered, and both cases return the same 401.

## Configuration

`auth.Config` holds the values; `auth.ConfigFromEnv` reads them, and the
script makes `server.LoadConfigFromEnv` call it:

| Variable | Default | Meaning |
| --- | --- | --- |
| `AUTH_SECRET_KEY` | required | signing key, at least 32 bytes; `AUTH_SECRET_KEY_FILE` names a file holding it instead |
| `AUTH_ISSUER` | `api` | `iss` claim |
| `AUTH_AUDIENCE` | the issuer | `aud` claim |
| `AUTH_ACCESS_TOKEN_TTL` | `15m` | access token lifetime, a Go duration |
| `AUTH_REFRESH_TOKEN_TTL` | `12h` | refresh token lifetime, a Go duration |
| `AUTH_COOKIE_SECURE` | `true` | `Secure` attribute of the refresh cookie; set `false` only for plain HTTP development |

`Config.Validate` runs in `Init`, so a bad value fails boot. The cookie uses
`SameSite=Lax`; change `CookieSameSite` in `ConfigFromEnv` if a cross-site
frontend needs `None`, which also requires a secure cookie.

## Registration

The script makes these edits outside the module and `go build` proves them:

- `internal/server/server.go`: `auth.NewModule(c.AuthConfig, pool)` in the
  `allModules` slice, plus the import.
- `internal/server/config.go`: the field `AuthConfig auth.Config`, and
  `LoadConfigFromEnv` calling `auth.ConfigFromEnv()`.
- `internal/modules/contracts.go`: the `Auth` interface with
  `VerifyAccessToken(ctx, token) (uuid.UUID, error)` and the field
  `Auth Auth` on `Contracts`.
- `envrc.template` and `compose.yaml`: the `AUTH_*` variables.

The script only edits the stock forms of `config.go` and `contracts.go`. When
a project already changed them, it stops and names the file; make the edit
above by hand, then run `go generate ./internal/modules/auth/...`, `go mod
tidy`, `go build ./...`, and `go vet ./...` from `api/`.

`Contracts.Verify` is left untouched on purpose. `testkit.Env.Wire` runs the
same phases as the server, so a nil check for `Auth` there would fail every
other module's isolated integration test. A consumer checks the contract in
its own `Connect` instead, as shown below.

## Consuming the contract

Another module protects its routes by asking auth to verify the bearer token.
It never imports the auth module, only the contract:

1. Keep the contract in `Connect`, which runs after every module published:

   ```go
   func (m *Module) Connect(_ context.Context, c *modules.Contracts) error {
   	if c.Auth == nil {
   		return errors.New("brand needs the auth contract")
   	}

   	m.auth = c.Auth
   	return nil
   }
   ```

2. Build a strict middleware from it and pass it to `Register` in
   `RegisterHTTP`. The generated `StrictMiddlewareFunc` gets the operation
   id, so a module can leave some operations public:

   ```go
   func NewBearerMiddleware(auth modules.Auth) server.StrictMiddlewareFunc {
   	return func(next server.StrictHandlerFunc, _ string) server.StrictHandlerFunc {
   		return func(ectx *echo.Context, request any) (any, error) {
   			scheme, token, found := strings.Cut(ectx.Request().Header.Get("Authorization"), " ")
   			if !found || !strings.EqualFold(scheme, "Bearer") {
   				ectx.Response().Header().Set("WWW-Authenticate", "Bearer")
   				return nil, ectx.JSON(http.StatusUnauthorized, server.ErrorResponse{Slug: "bearer-token-missing", Message: "A bearer access token is required"})
   			}

   			userUUID, err := auth.VerifyAccessToken(ectx.Request().Context(), token)
   			if err != nil {
   				ectx.Response().Header().Set("WWW-Authenticate", "Bearer")
   				return nil, ectx.JSON(http.StatusUnauthorized, server.ErrorResponse{Slug: "invalid-access-token", Message: "The access token is invalid or expired"})
   			}

   			ctx := app.ContextWithCaller(ectx.Request().Context(), userUUID)
   			ectx.SetRequest(ectx.Request().WithContext(ctx))

   			return next(ectx, request)
   		}
   	}
   }
   ```

   Returning a nil response with a nil error after writing the 401 is how the
   generated strict handler ends a request early.

3. Store the caller as a plain `uuid.UUID` value. Another module's identifier
   is never a foreign key across schemas.

The consumer's integration tests wire the auth module first, then their own
module, and log in through the auth client to get a token. Alternatively they
set `env.Contracts.Auth` to a small stub before `Wire` when the tests do not
exercise authentication.

## Generated code

`task gen` from the project root, or `go generate ./internal/modules/auth/...`
from `api/`, regenerates the server, the client, and the sqlc models. Never
edit generated files. Change `openapi.yaml` or the SQL and regenerate. A new
route is protected by default; add its operation id to `publicOperations` in
`middleware.go` to open it.
